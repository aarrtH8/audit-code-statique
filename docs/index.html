Audit de code statique

Un rapport utilisable, pas une liste d'alertes sans priorité.
Arthur Grossi EI — audit, sécurisation et reprise de code existant.

La plupart des audits annoncent « 47 vulnérabilités ». Ça ne dit ni lesquelles comptent, ni dans quel ordre les traiter. Je fais l'inverse : chaque constat est classé entre motif détecté (à examiner) et problème confirmé (vérifié en contexte).

Comment un rapport est structuré

#NiveauFichier:LigneConstat
1CONFIRMÉapi/users.js:42Requête SQL concaténée avec une entrée utilisateur — injectable.
2MOTIFui/render.js:118innerHTML sur données serveur — à vérifier : échappement en amont ?
3MOTIFREADME.md:7Chaîne d'exemple qui ressemble à une clé — documentation, pas un secret.

La 3e ligne n'est pas un risque : c'est un exemple. Compter cette ligne comme une « vulnérabilité » serait malhonnête. C'est précisément ce que mon rapport ne fait pas.

Ce qui est livré

  • Périmètre : fichiers, langages, dépendances, points d'entrée.
  • Constats : chaque ligne avec fichier:ligne et recommandation.
  • Classification : motif détecté vs problème confirmé en contexte.
  • Limites : ce qui n'a pas été analysé, et pourquoi.
  • Effort : estimation de remise en état, par lot priorisé.

Conditions

  • Échantillon gratuit sur 1 à 3 fichiers que vous désignez — vous jugez la qualité sur du code réel, sans engagement.
  • Devis ensuite, selon le volume. Montant et devise fixés ensemble avant tout travail payant.
  • Paiement : PayPal ou virement professionnel. Pas de cryptomonnaie.

Je ne garantis pas l'absence de défaut : un audit réduit l'incertitude, il ne l'annule pas. Aucun prestataire honnête ne peut promettre un code sans faille.

Une preuve, pas une promesse

J'applique la méthode à mon propre outillage et je publie le résultat — y compris les défauts trouvés, dont deux faux positifs que mon propre moteur produisait. Un rapport que je n'ose pas appliquer à moi-même n'a aucune valeur pour vous.
