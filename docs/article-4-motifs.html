4 motifs de code qui signalent un vrai problème — et comment les repérer avant la mise en production

*Article publié par un développeur qui vend des audits de code. Je le dis d'emblée : ce texte a un but

commercial. Il est aussi exact, et il est utile tout seul. Si vous ne me payez jamais, vous en sortirez

avec 4 vérifications que vous pouvez faire en dix minutes.*

Pourquoi ces 4 motifs, et pas 20

Sur un dépôt réel, une analyse statique remonte des dizaines de signalements. La plupart ne sont pas

des urgences. Les quatre motifs ci-dessous partagent une propriété : quand ils sont présents, **le

problème est presque toujours réel**, pas théorique.

1. Un secret dans le code source


const apiKey = "sk_live_…";
const DB_PASSWORD = "…";

Pourquoi c'est grave : ce n'est pas seulement que la clé est visible. C'est qu'elle est dans

l'historique Git, donc dans chaque clone, chaque sauvegarde, chaque fork. La supprimer du fichier

ne la retire pas de l'historique.

Ce qu'il faut faire, dans cet ordre :

  1. Révoquer la clé. D'abord. Pas après le nettoyage — avant.
  2. La régénérer et la placer dans une variable d'environnement.
  3. Vérifier que le .env est bien dans .gitignore.
  4. Seulement ensuite, s'inquiéter de l'historique.

Vérification rapide — dans votre dépôt :


git log -p --all -S 'password' -- '*.js' '*.py' '*.env' | head -50

2. Une requête SQL construite par concaténation


db.query("SELECT * FROM users WHERE id = " + userId);

Pourquoi c'est grave : la valeur d'entrée se retrouve interprétée comme du SQL. Ce n'est pas une

question de « peut-être un jour » — c'est la définition même de l'injection SQL.

La correction est mécanique :


db.query("SELECT * FROM users WHERE id = ?", [userId]);

Vérification rapide :


grep -rnE '(SELECT|INSERT|UPDATE|DELETE)[^;]*\+' --include='*.js' --include='*.py' .

Attention au faux positif fréquent : "SELECT * FROM " + TABLE_NAME avec une constante n'est pas

une injection. La question à poser est toujours : cette valeur vient-elle de l'extérieur ?

3. Une commande système dont l'argument vient de l'appelant


execSync("tar -czf backup.tgz " + nomFichier);

Pourquoi c'est grave : selon la provenance de nomFichier, on peut transformer un nom de fichier

en commande arbitraire. Le point clé n'est pas le style — c'est d'où vient la valeur.

La forme sûre, quand c'est possible :


execFileSync("tar", ["-czf", "backup.tgz", nomFichier]);

Ici il n'y a plus d'interprétation par un shell : chaque argument est passé tel quel.

Vérification rapide :


grep -rnE '(exec|execSync|spawn)\([^,)]*\+' --include='*.js' .

4. eval() sur une donnée qui n'est pas un littéral


const data = eval("({ endpoint: '" + url + "' })");

Pourquoi c'est grave : eval exécute du code. Si la chaîne contient une entrée externe, c'est de

l'exécution de code à distance, sans les protections d'un parseur.

Dans le cas ci-dessus, JSON.parse suffit — comme dans la très grande majorité des eval qu'on

rencontre en pratique.

Vérification rapide :


grep -rn 'eval(' --include='*.js' --include='*.ts' . | grep -v 'eval(JSON'

Ce que ces 4 motifs ne disent pas

Ils ne disent pas que votre application est vulnérable. Ils disent : *voici quatre points à

vérifier, à des endroits précis de votre code*. Un audit honnête fait la même distinction. Toute

personne qui vous vend « 47 vulnérabilités critiques » à partir d'un scan automatique vous vend un

chiffre, pas un diagnostic.

Une analyse statique est un filtre, pas un verdict. La valeur est dans le tri : ce qui compte,

ce qui peut attendre, ce qui est un faux positif.
