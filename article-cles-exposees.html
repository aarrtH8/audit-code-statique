Vérifier qu'une clé d'API n'est pas exposée dans votre dépôt

Écrit pour les développeurs et les indépendants qui ont du code public ou partagé. Aucune inscription, aucun outil à installer.

Si votre dépôt est public et qu'une clé y a été poussée : des robots scannent GitHub en continu. Une clé AWS valide est exploitée en général en quelques minutes — pas en quelques jours. Supprimer le fichier ne suffit pas : l'historique Git conserve tout. La seule vraie remédiation est de révoquer la clé, pas de la cacher.

1. Chercher les motifs, pas les noms de fichiers

On trouve rarement « secret.txt ». On trouve une chaîne qui ressemble à une clé, au milieu d'un fichier normal. Ces commandes cherchent dans tout l'historique, y compris les commits anciens et les branches supprimées.

# Clés AWS (AKIA...)
git log -p --all | grep -E "AKIA[0-9A-Z]{16}"

# Clés Stripe
git log -p --all | grep -E "sk_(live|test)_[0-9a-zA-Z]{24,}"

# Clés OpenAI
git log -p --all | grep -E "sk-[A-Za-z0-9]{20,}T3BlbkFJ"

# Clés Google API
git log -p --all | grep -E "AIza[0-9A-Za-z_\-]{35}"

# Un bloc de clé privée, quelle que soit son origine
git log -p --all | grep -n "BEGIN .* PRIVATE KEY"

Ces motifs viennent du projet open source gitleaks, qui en maintient plusieurs centaines. Si une des commandes renvoie une ligne, ne la copiez pas ici : traitez-la comme compromise dès maintenant.

2. Le piège du fichier supprimé

Beaucoup de gens supposent que retirer un fichier dans un commit le fait disparaître. C'est faux : git log -p remonte toute la chaîne. Vérifiez explicitement :

# Le fichier est-il encore joignable dans l'historique ?
git log --all --full-history -- .env
git log --all --full-history -- "*.pem" "*.key" "config/secrets*"

Si l'un de ces fichiers apparaît, il est toujours lisible par quiconque clone le dépôt. Changer le mot de passe ou la clé est obligatoire. Réécrire l'historique (git filter-repo, BFG) est un nettoyage, pas une protection : entre la publication et le nettoyage, la clé a déjà pu être aspirée.

3. Les fichiers que Git ne devrait jamais suivre

Beaucoup de fuites viennent d'un .gitignore incomplet. Vérifiez que ces motifs y sont :

.env
.env.*
!.env.example
*.pem
*.key
*.p12
id_rsa*
config/secrets.*
credentials.json
serviceAccount*.json

Vérifiez ensuite ce qui est effectivement suivi, .gitignore ou pas :

git ls-files | grep -iE "\.env|secret|credential|\.pem|\.key|id_rsa"

Un fichier déjà suivi reste suivi même si vous l'ajoutez au .gitignore ensuite. Il faut git rm --cached fichier — et la clé reste à révoquer.

4. Côté navigateur : le code livré est public

Tout ce qui part dans un bundle JavaScript est lisible par n'importe qui avec F12. Une clé placée dans du code front (même « obfusquée ») est publique. Idem pour les variables préfixées qui sont volontairement exposées par le framework (par exemple NEXT_PUBLIC_*, VITE_*, REACT_APP_* selon la configuration).

# Chercher des chaînes sensibles dans le build livré
grep -rEo "(AKIA[0-9A-Z]{16}|sk_(live|test)_[0-9a-zA-Z]{24,}|AIza[0-9A-Za-z_\-]{35})" dist/ build/

Si ça ressort, la clé est chez le client final. Révocation immédiate, puis passage par un proxy serveur qui garde le secret côté back.

5. Ce que je ne prétends pas

Ces commandes trouvent des motifs. Elles ne prouvent pas qu'une clé est encore active, ni qu'elle a été exploitée. Elles ne remplacent pas une revue du code : une clé peut être correctement stockée en base et malgré tout fuiter par une route qui la renvoie sans contrôle d'accès. Trouver un motif n'est pas confirmer une vulnérabilité — c'est un indice à vérifier.

Ces commandes suffisent-elles ? Souvent oui, pour les fuites les plus courantes. Elles ne couvrent pas les problèmes de logique : une route d'API sans contrôle de propriétaire, un jeton vérifié sans signature, un SELECT construit par concaténation. Ces-là demandent de lire le code, pas de chercher un motif.
